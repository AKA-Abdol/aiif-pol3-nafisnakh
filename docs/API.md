# API نفیس‌نخ — راهنمای تیم فرانت

نسخه ۰٫۲٫۰ · `http://127.0.0.1:8000` · مستندات تعاملی `/docs` · اسکیمای خام `/openapi.json`

۱۶ مسیر، ۱۷ عملیات. همهٔ نمونه‌های این سند خروجی واقعی سرور با `as_of=2021-06-30` هستند.

---

## سه چیزی که قبل از هر چیز باید بدانید

### ۱. هر عدد یک شاهد دارد

هر جملهٔ فارسی که سیستم تولید می‌کند به یک یا چند **شناسهٔ شاهد** وصل است:

```
EV-C_126481-loop-offer-001
   └ مشتری ┘└ نوع ادعا ┘└شماره┘
```

و هر شناسه را می‌شود با `/evidence/{id}/rows` تا **ردیف‌های واقعی دیتابیس** باز کرد.

**پیامد:** یک کامپوننت مشترک `EvidenceChip` بسازید که شناسه می‌گیرد و یک drawer باز می‌کند. در همهٔ صفحه‌ها استفاده می‌شود.

### ۲. همه‌چیز نسبت به `as_of` است

سیستم «امروز» را نمی‌بیند. هر پاسخ نسبت به یک تاریخ مبنا حساب شده و فقط داده‌ای را می‌بیند که **در آن تاریخ منتشر شده بود** — نه داده‌ای که آن روز اتفاق افتاده.

هر مسیر پارامتر اختیاری `?as_of=YYYY-MM-DD` دارد. آن را در state سراسری نگه دارید و به همهٔ درخواست‌ها اضافه کنید. تغییرش یعنی کل کش کلاینت باطل می‌شود.

### ۳. سه مسیر پول خرج می‌کنند

| مسیر | هزینه |
|---|---|
| `GET /actions` | یک فراخوان مدل به ازای هر اقدام (پیش‌فرض ۲۵) |
| `GET /report` | همان صف، همان هزینه |
| `POST /customers/{id}/meeting` | ۲ فراخوان به ازای هر تحلیل‌گر بیدار |
| `POST /customers/{id}/action` | ۱ تا ۲ فراخوان — فقط برای همان یک مشتری |
| بقیهٔ ۱۵ عملیات | رایگان |

نتیجه‌ها روی سرور کش می‌شوند؛ فراخوان دوم فوری است. ولی اجرای اول ممکن است چند دقیقه طول بکشد.

**هیچ مسیر پولی نباید با باز شدن صفحه یا refresh خودکار صدا زده شود.**

**ولی این جدول برای شماست، نه برای کاربر.** تعداد فراخوان مدل، وضعیت کش و کلمهٔ
«رایگان» هیچ‌کدام روی صفحه نمی‌آیند: مخاطب مدیر فروش است و این‌ها جزئیات عملیاتی
ماست، نه تصمیم او. چیزی که او لازم دارد **مدت انتظار** است — همان و بس، در
کوچک‌ترین قلم صفحه (`RunHint`). دکمه‌ای که کاربر را از کار مفید می‌ترساند بدتر از
دکمه‌ای است که چند ثانیه طول می‌کشد.

## واژه‌نامه

| اصطلاح | در پاسخ | یعنی |
|---|---|---|
| سطل | `bucket` | `grow` · `protect` · `fix` · `reduce` — تصمیم راهبردی دربارهٔ مشتری |
| سیگنال | `signals[]` | خروجی یکی از ۲۸ آشکارساز؛ شدت ۰–۱۰۰، دستهٔ `risk`/`opportunity`/`efficiency` |
| شاهد | `evidence[]` | ادعای قابل ردیابی؛ `claim_fa` جملهٔ آماده، `locator` یعنی قابل باز شدن |
| RFM | `rfm` | جایگاه در کل دفتر؛ `rfm_cell` مثل `"545"` |
| حلقهٔ باز | `open_loops` | کارهایی که **ما** نیمه‌کاره گذاشته‌ایم — چهار نوع |
| گیت | `gates` | دو قید بازدارنده: `credit_room` و `open_investigation` |
| تحلیل‌گر | `agents[]` | یکی از ۷ عامل؛ روتر قطعی تصمیم می‌گیرد کدام اجرا شود |

# مرجع مسیرها

## `GET /health`

سرور بالاست؟ تاریخ مبنا چیست؟ کلید مدل تنظیم شده؟

```json
{
  "status": "ok",
  "as_of": "2021-06-30",
  "llm_available": true,
  "llm_model": "google/gemini-3.7-flash",
  "llm_provider": ["google-vertex/global"],
  "cached_runs": ["2021-06-30|quadrant|-"]
}
```

`llm_available: false` یعنی کلید تنظیم نیست — مسیرهای پولی همچنان جواب می‌دهند ولی با متن قالبی، نه با مدل. `cached_runs` می‌گوید کدام محاسبات روی سرور آماده‌اند، پس می‌فهمید فراخوان بعدی سریع است یا کند.

**فرانت:** در بوت یک بار. اگر شکست خورد، «سرور در دسترس نیست» و بقیهٔ درخواست‌ها را نزنید. `llm_available` را در state نگه دارید تا اگر `false` بود کنار دکمهٔ ساخت دستور جلسه هشدار بگذارید.

## `GET /summary`

یک نگاه به کل دفتر.

```json
{
  "as_of": "2021-06-30",
  "customers": 526,
  "signals": 2083,
  "triggered_customers": 523,
  "detectors": 28,
  "quadrants": { "protect": 204, "grow": 178, "reduce": 79, "fix": 65 },
  "evidence": 10747,
  "metric_tables": ["cadence", "payment", "quality", "engagement", "mix",
                    "economics", "wallet", "rfm", "open_loops",
                    "llm_complaints", "llm_resolutions"],
  "feedback_weights": {}
}
```

**فرانت:** ردیف بالای داشبورد. `quadrants` تصویر راهبردی کل کسب‌وکار است — به‌شکل نمودار میله‌ای چهارتایی نشان دهید و هر میله را به فهرست مشتریان با همان فیلتر لینک کنید.

## `GET /customers`

فهرست دفتر، با همان‌قدر اطلاعات که برای انتخاب یک مشتری لازم است.

**پارامترها**

| نام | نوع | توضیح |
|---|---|---|
| `as_of` | date | اختیاری |
| `bucket` | enum | `grow` · `protect` · `fix` · `reduce` |
| `segment` | string | بخش مشتری، مثل `A` |
| `limit` | int | ۱ تا ۱۰۰۰، پیش‌فرض ۱۰۰ |

```json
{
  "as_of": "2021-06-30",
  "total": 526,
  "customers": [
    { "customer_id": "C_113139", "bucket": "fix", "segment": "A",
      "rfm_cell": "555", "rfm_segment_fa": "مشتری کلیدی",
      "open_loops": 5.0, "signals": 13 }
  ]
}
```

مرتب‌سازی سمت سرور بر اساس تعداد سیگنال (نزولی). `total` تعداد کل قبل از `limit` است.

> **صفحه‌بندی ندارد.** پارامتر `offset` وجود ندارد. برای ۵۲۶ مشتری همه را یک‌بار با `limit=1000` بگیرید و جست‌وجو و صفحه‌بندی را سمت کلاینت انجام دهید.

**فرانت:** جدول صفحهٔ مشتریان. ستون‌ها: شناسه، سطل، RFM، حلقهٔ باز، سیگنال. فیلترها بالای جدول. کلیک روی سطر → پروندهٔ ۳۶۰.

---

## `GET /customers/{customer_id}`

همه‌چیزی که پروندهٔ ۳۶۰ از آن ساخته می‌شود. **مهم‌ترین مسیر برنامه.**

**ساختار**

| کلید | محتوا |
|---|---|
| `customer_id`, `as_of` | شناسه و تاریخ مبنا |
| `bucket` | `grow`/`protect`/`fix`/`reduce` |
| `bucket_reason_fa` | جملهٔ فارسی آماده که چرا این سطل |
| `rfm` | ۱۳ کلید — `recency_days`، `r_score`/`f_score`/`m_score`، `rfm_cell`، `rfm_segment_fa`، `median_order_value` |
| `open_loops` | ۲۰ کلید — چهار حلقه با شمارش، سن، و **شناسهٔ ردیف‌ها** |
| `payment` | ۲۵ کلید — `open_exposure`، `exposure_ratio`، `dso`، `bounces`، `credit_room_state` |
| `quality` | ۲۹ کلید — شکایات، برگشتی، شعاع انفجار همبافت، فرار آزمایشگاهی |
| `signals[]` | آرایهٔ سیگنال‌ها |
| `evidence[]` | آرایهٔ کامل شواهد (۳۹ مورد برای C_126481) |
| `relationship` | ممکن است `null` باشد — فقط برای مشتریان صف اقدام ساخته می‌شود |

**شکل یک سیگنال**

```json
{
  "id": "SIG-C_126481-cadence_breach",
  "customer_id": "C_126481",
  "detector": "cadence_breach",
  "category": "risk",
  "severity": 100.0,
  "direction": "deteriorating",
  "headline_fa": "سکوت خرید 175.1 برابر ریتم شخصی این مشتری (387 روز بدون خرید).",
  "evidence_ids": ["EV-C_126481-cadence-ratio-001", "..."],
  "first_detected_at": "2021-06-30",
  "value_at_stake": 2102198.53,
  "suggested_bucket": null,
  "detail": { "ratio": 175.07, "days_since_last": 387.0 }
}
```

`category` یکی از `risk` · `opportunity` · `efficiency`.
`direction` یکی از `deteriorating` · `improving` · `static`.

**شکل یک شاهد**

```json
{
  "id": "EV-C_126481-cadence-last-001",
  "customer_id": "C_126481",
  "kind": "metric",
  "claim_fa": "آخرین خرید 387 روز پیش بوده است (تاریخ 2020-06-08).",
  "value": 387.0,
  "unit": "روز",
  "as_of": "2021-06-30",
  "window": ["2020-06-30", "2021-06-30"],
  "source_rows": "فاکتورها:T_653555,T_915931,T_798084,T_845068",
  "provenance": { "formula": "as_of - max(تاریخ فاکتور)", "n_invoices": 58 },
  "confidence": 1.0,
  "locator": { "kind": "ids", "sheet": "فاکتورها",
               "key": "شماره فاکتور", "values": ["T_653555", "..."] }
}
```

`kind` یکی از `metric` · `event` · `text` · `comparison`.

دو فیلد که باید در UI دیده شوند:
- `confidence < 1.0` — عدد قطعی نیست، یک نشان کنارش بگذارید
- `provenance.assumption === true` — بر پایهٔ فرض پیکربندی است نه اندازه‌گیری؛ این باید صریح‌تر دیده شود

**فرانت:** یک بار بگیرید و در state نگه دارید. `evidence[]` را به `Map<id, evidence>` تبدیل کنید تا `EvidenceChip` بدون درخواست شبکه متن ادعا را در tooltip نشان دهد.

## `GET /customers/{customer_id}/page`

همان پروندهٔ ۳۶۰، ولی یک صفحهٔ HTML کامل که سرور رندر کرده.

خروجی `text/html`، حدود ۳۰۰ کیلوبایت، **بدون هیچ وابستگی خارجی** — نه CDN، نه فونت بیرونی، نه فراخوان API. از پیوست ایمیل و روی موبایل بدون شبکه باز می‌شود.

پارامتر `rows` (۱ تا ۲۰۰، پیش‌فرض ۲۵): حداکثر ردیف نمایش‌داده‌شده از هر شاهد.

**فرانت:** داخل برنامه رندر نکنید. یک دکمهٔ «نسخهٔ قابل ارسال» که در تب جدید بازش می‌کند. کاربردش این است که مدیر فروش برای مشتری بفرستد یا سر جلسه آفلاین باز کند. نسخهٔ داخل برنامه را خودتان از `/customers/{id}` بسازید تا تعاملی باشد.

## `GET /evidence/{evidence_id}/rows`

ردیف‌های واقعی دیتابیس پشت یک ادعا. **مهم‌ترین مسیر این API.**

کل قرارداد شواهد برای همین وجود دارد: پیشنهادی که به مشتری نشان داده می‌شود باید تا رکوردهایی که رویشان ایستاده باز شود. drill-down هم با همان تاریخ مبنا گیت شده که خود محاسبه بود.

```json
{
  "evidence_id": "EV-C_126481-loop-offer-001",
  "claim_fa": "7 آفر بدون پاسخ مانده که مهلت اعتبار خودش را رد کرده است...",
  "as_of": "2021-06-30",
  "locator": { "kind": "ids", "sheet": "آفرها", "key": "Offer_ID", "values": ["..."] },
  "n_rows": 7,
  "columns": ["Offer_ID", "Customer_ID", "Offer_Date", "Available_At",
              "Product_ID", "گروه کالا", "Base_Price_per_unit",
              "Offered_Price_per_unit", "Offer_Discount_Pct", "Offer_Type",
              "Validity_Days", "Offer_Reason", "Result",
              "Decision_At", "Decision_Available_At", "Source_System"],
  "rows": [
    { "Offer_ID": "OFF-0000520", "Customer_ID": "C_126481",
      "Offer_Date": "2020-02-23", "Base_Price_per_unit": 56.4, "...": "..." }
  ]
}
```

`limit` (۱ تا ۵۰۰، پیش‌فرض ۵۰). `n_rows` تعداد کل است، نه تعداد برگشتی.

**خطاها**

| کد | یعنی | در UI |
|---|---|---|
| `404` | شناسه وجود ندارد | «این شاهد یافت نشد» — احتمالاً `as_of` عوض شده |
| `409` | شاهد locator ندارد | نباید اتفاق بیفتد؛ به بک‌اند گزارش دهید |

> **ستون‌ها ثابت نیستند.** `columns` بسته به شیتی که شاهد به آن اشاره می‌کند فرق می‌کند — فاکتورها، آفرها، شکایات، درخواست توسعه، تعاملات CRM، کیفیت لات. جدول را **پویا** از روی `columns` بسازید. نام ستون‌ها گاهی فارسی است و گاهی انگلیسی؛ همان‌طور که آمده نشان دهید.

**فرانت:** یک `EvidenceDrawer` که با کلیک روی `EvidenceChip` باز می‌شود. بالا جملهٔ `claim_fa`، زیرش `provenance.formula` با فونت مونو، بعد جدول ردیف‌ها با `overflow-x: auto`. یک دکمهٔ «خروجی CSV» هم بگذارید — دقیقاً همان چیزی است که کاربر می‌خواهد به مشتری نشان دهد.

## `GET /tools`

هشت ابزاری که یک تحلیل‌گر می‌تواند از طریق آنها به داده برسد.

```json
{
  "tools": [
    { "name": "get_dev_requests",
      "description_fa": "درخواست‌های توسعه این مشتری: نوع، وضعیت، تاریخ تصمیم و سن هر درخواست.",
      "params": { "limit": "حداکثر تعداد درخواست (پیش‌فرض ۸، جدیدترین اول)" },
      "schema": { "…OpenAI function-calling shape…": null } }
  ]
}
```

هشت ابزار: `get_dev_requests` · `get_complaints` · `get_crm_promises` · `get_payment_state` · `get_lab_band_position` · `get_market_context` · `get_peer_comparison` · `get_offer_history`

**فرانت:** صفحهٔ سلامت سیستم یا modal راهنما. کاربر نهایی به آن نیاز ندارد، ولی برای دیباگ و برای نشان دادن «سیستم به چه چیزی نگاه می‌کند» ارزش دارد.

```json
    "evidence_ids": ["EV-C_126481-exposure-001", "EV-C_126481-dso-001",
                     "EV-C_126481-finance-net-001"],
    "payload": { "open_exposure": 298524.49, "credit_limit": 213000,
                 "exposure_ratio": 1.4015, "dso": 26.87, "bounces": 0.0,
                 "credit_room_state": "exhausted",
                 "net_finance_effect": -95714.29 },
    "note_fa": "سقف اعتبار در این دفتر دو مقیاسی است؛ نسبت اشغال معنا دارد...",
    "empty_reason_fa": "",
    "model_text": "ابزار: get_payment_state · مشتری C_126481\n[EV-...] ..."
  }]

```

پارامتر اختیاری `?tool=get_payment_state` فقط یکی را اجرا می‌کند. بدون آن، هر هشت‌تا.

| فیلد | استفاده |
|---|---|
| `claims` + `evidence_ids` | نمایش به کاربر — هم‌طول و یک‌به‌یک متناظر |
| `payload` | ساختن نمودار و شاخص عددی |
| `note_fa` | محدودیت داده؛ اگر پر بود حتماً زیر نتیجه نشانش دهید |
| `empty_reason_fa` | اگر پر بود یعنی چیزی پیدا نشد و این جمله می‌گوید چرا |
| `model_text` | فقط دیباگ — متن خامی که به مدل داده می‌شود |

**فرانت:** پروندهٔ ۳۶۰، یک تب به اسم «آنچه سیستم دیده». هشت کارت، هرکدام با فهرست claims و `EvidenceChip`، و `note_fa` در پانویس. این بخش اعتماد می‌سازد: کاربر می‌بیند سیستم به چه نگاه کرده، پیش از خواندن نتیجه.

| فیلد | معنی |
|---|---|
| `routed[]` | تحلیل‌گرهایی که اجرا خواهند شد، به همان ترتیبی که در دستور جلسه می‌آیند |

## `GET /customers/{customer_id}/action`

**رایگان.** اقدام این مشتری را فقط از کش روی دیسک می‌خواند. هیچ‌وقت چیزی نمی‌سازد،
پس refresh مرورگر هزینه‌ای ندارد.

```json
{
  "customer_id": "C_126481",
  "as_of": "2021-06-30",
  "status": "not_computed",
  "result": null,
  "estimated_llm_calls": 2
}
```

`status`:

| مقدار | یعنی |
|---|---|
| `ready` | اقدام آماده است و داخل `result` آمده |
| `not_computed` | چیزی ساخته نشده — یا آنچه ساخته شده کهنه شده. `POST` می‌سازدش |
| `dropped` | ساخته شد ولی از اعتبارسنجی شواهد رد نشد و منتشر نشده |

اگر این مشتری در صف امروز باشد، اقدامش همان‌جا ساخته شده و این مسیر همان را
برمی‌گرداند — نه اینکه دوباره بسازد. صف هنگام ساخته‌شدن، اقدام هر مشتری را در همین
کش می‌نویسد، پس بعد از ری‌استارت هم همان جواب سر جایش است.

`estimated_llm_calls` هزینهٔ یک `POST` در همین لحظه است — روی دکمه بنویسیدش. اگر
جمع‌بندی رابطه از قبل موجود باشد ۱ است، وگرنه ۲. کف است نه سقف: درفت مردود در
اعتبارسنجی یک بار دیگر تلاش می‌شود، دقیقاً مثل صف.

## `POST /customers/{customer_id}/action`

**هزینه دارد.** برای یک مشتری، تمام محاسبات اقدام را انجام می‌دهد — حتی اگر آن
مشتری در صف روزانه نبوده باشد.

اگر اقدام این مشتری از قبل موجود باشد — چه از یک `POST` قبلی، چه از ساخت صف —
همان برگردانده می‌شود و چیزی دوباره ساخته نمی‌شود. فقط `refresh=true` از این قاعده
مستثناست.

چرا لازم است: صف روزانه در `top_n` قطع می‌شود. حسابی که رتبه‌اش پایین‌تر است همهٔ
ورودی‌هایش حساب شده ولی هیچ اقدامی برایش نوشته نشده. این مسیر همان یکی‌دو فراخوان
را می‌پردازد.

| پارامتر | پیش‌فرض | کار |
|---|---|---|
| `as_of` | تاریخ مبنای پیکربندی | مثل بقیهٔ مسیرها |
| `refresh` | `false` | حتی اگر کش تازه باشد دوباره بساز — **دوباره هزینه دارد** |

پاسخ همان شکل `GET` است، با `result` پر:

```json
{
  "customer_id": "C_126481",
  "as_of": "2021-06-30",
  "status": "ready",
  "result": {
    "action": { "rank": 47, "priority": "بالا", "title_fa": "…", "evidence_ids": ["EV-…"] },
    "relationship": { "health": "شکننده", "recommended_tone_fa": "…" },
    "dropped": [],
    "n_llm_calls": 2,
    "call_sources": ["cached", "live"],
    "served_from": "computed",
    "computed_at": "2026-08-21T09:14:00+00:00",
    "model": "google/gemini-3.7-flash"
  },
  "estimated_llm_calls": 0
}
```

سه نکته که فرانت باید بداند:

* **`action.rank` جایگاه این حساب در کل دفتر است، نه ۱.** یک بیلد تک‌حسابی رتبه را
  از رتبه‌بندی کل کتاب برمی‌دارد؛ اگر جایی ۱ دیدید باگ است.
* **نتیجه روی دیسک کش می‌شود** (`cache/actions/<as_of>/<id>.json`). فشار دوم رایگان
  است، و بعد از ری‌استارت سرور هم رایگان می‌ماند — برخلاف کش درون‌حافظه‌ای اجراها.
* **کهنگی با اثر انگشت تعیین می‌شود، نه با زمان.** مدل فعال و وزن‌های بازخورد داخل
  اثر انگشت‌اند؛ با هر `POST /feedback` وزن‌ها جابه‌جا می‌شوند و اقدام‌های کش‌شده
  خودبه‌خود `not_computed` می‌شوند.

`served_from: "cache"` یعنی این پاسخ هیچ هزینه‌ای نداشت. `call_sources` می‌گوید از
آن فراخوان‌ها کدام واقعاً به مدل رسید (`live`) و کدام از کش prompt آمد (`cached`)
یا اصلاً مدل نبود (`rules`).

هر یک از ۲۸ آشکارساز روی چند درصد از جمعیت واجد شرایطش شلیک می‌کند.

```json
{
  "as_of": "2021-06-30",
  "population": 526,
  "rows": [
    { "detector": "volume_decline", "category": "risk",
      "fired": 185, "eligible": 331, "fire_rate": 0.5589,
```

**فرانت:** صفحهٔ سلامت سیستم — برای مدیر محصول و تیم داده، نه مدیر فروش. جدول مرتب بر اساس `fire_rate` با نوار افقی. اگر `failures` خالی نبود، در هدر برنامه نشان هشدار بگذارید.

## `POST /feedback`

ثبت تصمیم مدیر فروش دربارهٔ یک اقدام. **تنها مسیری که می‌نویسد.**

```json
{
  "customer_id": "C_245948",
  "decision": "done",
  "detectors": ["cadence_breach"],
  "reason_fa": "با مشتری تماس گرفتیم، قرار شد تا هفتهٔ بعد تسویه کند",
  "actor": "مدیر فروش",
  "rank": 1,
  "bucket": "protect"
}
```

`decision` یکی از `done` · `dismissed` · `snoozed` · `wrong`.

```json
{
  "recorded": { "customer_id": "...", "decision": "done", "detectors": ["..."],
                "as_of": "2021-06-30", "recorded_at": "...", "rank": 1 },
  "weights": { "cadence_breach": 1.12 }
}
```

> **خطای ۴۰۰ که حتماً می‌بینید.** اگر `detectors` را نفرستید، سرور تلاش می‌کند از صف اقدام فعلی پیدایش کند؛ اگر آن مشتری در صف نباشد `400` برمی‌گردد. **راه‌حل:** همیشه `detectors` را از همان کارتی که کاربر رویش کلیک کرده بفرستید — یعنی `action.signals`. بازخوردی که به آشکارساز نسبت داده نشود به رتبه‌بندی چیزی یاد نمی‌دهد، پس رد می‌شود نه اینکه بی‌صدا ذخیره شود.

> **کش سرور باطل می‌شود.** بعد از هر `POST /feedback` کش سمت سرور پاک می‌شود، چون صف بعدی باید با همین رأی رتبه‌بندی شود. یعنی فراخوان بعدی `/actions` دوباره پول خرج می‌کند. کش کلاینت خودتان را هم باطل کنید ولی صف را خودکار دوباره نگیرید — دکمهٔ «به‌روزرسانی صف» بدهید.

**فرانت:** روی هر کارت اقدام چهار دکمه — «انجام شد» · «رد شد» · «فعلاً نه» · «اشتباه است». دو تای آخر یک textarea برای `reason_fa` باز کنند. optimistic update بزنید و کارت را بلافاصله محو کنید.

## `GET /feedback`

آمار بازخوردها و وزن‌هایی که از آنها درآمده.

```json
{ "events": 0, "detector_stats": [], "weights": {} }
```

وزن هر آشکارساز در بازهٔ ۰٫۶۵ تا ۱٫۳۵ می‌ماند و مستقیماً در رتبه‌بندی صف ضرب می‌شود. زیر ۱۰ رویداد، آشکارساز وزن ۱٫۰ می‌گیرد — سکوت جریمه نیست.

**فرانت:** صفحهٔ سلامت سیستم. جدول: آشکارساز، تعداد رأی، تفکیک تصمیم‌ها، وزن فعلی. آنهایی که وزنشان زیر ۰٫۸ رفته را برجسته کنید — یعنی مدیر فروش مرتب می‌گوید اینها اشتباه‌اند.

# نقشهٔ صفحه‌ها

پنج صفحه. ترتیبشان ترتیب کار روزانهٔ مدیر فروش است.

## ۱. صف امروز — `/`

اولین چیزی که صبح می‌بیند. جواب یک سؤال: امروز به کدام مشتری‌ها زنگ بزنم و چه بگویم.

| بخش | فراخوان |
|---|---|
| نوار وضعیت | `GET /health` · `GET /summary` |
| فهرست اقدام‌ها | `GET /actions?limit=25` |
| دکمه‌های بازخورد روی هر کارت | `POST /feedback` |
| نسخهٔ چاپی | `GET /report` |

> این صفحه گران است. اول `/summary` (رایگان و سریع) را نشان دهید و صف را با skeleton و پیام «در حال ساخت صف — ممکن است چند دقیقه طول بکشد» بارگذاری کنید.

## ۲. مشتریان — `/customers`

| بخش | فراخوان |
|---|---|
| جدول اصلی | `GET /customers?limit=1000` |
| فیلترها (سطل، بخش، RFM، حلقهٔ باز) | بدون فراخوان — سمت کلاینت |

## ۳. پروندهٔ ۳۶۰ — `/customers/:id`

قلب برنامه.

| بخش | فراخوان |
|---|---|
| یک نگاه — ردیف کاشی‌ها | `GET /customers/:id` |
| سیگنال‌ها | از همان پاسخ — `signals[]` |
| حلقه‌های باز از سمت ما | از همان پاسخ — `open_loops` |
| آنچه سیستم دیده | `GET /customers/:id/tools` (تنبل، وقتی تب باز شد) |
| EvidenceDrawer | `GET /evidence/:id/rows` |
| نسخهٔ قابل ارسال | `GET /customers/:id/page` (تب جدید) |
| اقدام پیشنهادی | `GET /customers/:id/action` هنگام باز شدن · `POST` فقط با کلیک |

هفت کاشی «یک نگاه» همه از یک پاسخ می‌آیند: سطل + `bucket_reason_fa` · `rfm_cell` و `rfm_segment_fa` · درآمد و حاشیه · `payment.credit_room_state` · تعداد نوع حلقهٔ باز · `rfm.recency_days` · `quality.complaints_open`.

**حلقه‌های بسته را هم نشان دهید** با حالت خنثی — «الان به این مشتری چیزی بدهکار نیستیم» جوابی است که کاربر قبل از جلسه لازم دارد.

## ۴. آماده‌سازی جلسه — `/customers/:id/meeting`

دو مرحلهٔ صریح. **این تفکیک عمدی است و نباید در یک دکمه ادغام شود.**

| مرحله | فراخوان |
|---|---|
| ۱ — تصمیم روتر | `GET /customers/:id/meeting/plan` (رایگان) |
| ۲ — اجرا | `POST /customers/:id/meeting` (~۸۵ ثانیه) |
| کپی و چاپ | از همان پاسخ — `brief_fa` |

کارت هر یافته: عنوان از `question_fa`، «چرا ارجاع شد» از `trigger_fa`، «چه دید» از `tools_used` + `tools_reason_fa`، بدنه از `headline_fa` و `reasoning_fa` با شناسه‌های داخل متن تبدیل‌شده به chip، و `recommended_step_fa` در بلوک متمایز.

## ۵. سلامت سیستم — `/system`

برای مدیر محصول و تیم داده.

| بخش | فراخوان |
|---|---|
| کالیبراسیون آشکارسازها | `GET /calibration` |
| یادگیری از بازخورد | `GET /feedback` |
| ابزارها و تحلیل‌گرها | `GET /tools` · `GET /agents` |

## کامپوننت‌های مشترک

| کامپوننت | ورودی | کجا |
|---|---|---|
| `EvidenceChip` | `evidenceId` | همه‌جا — سیگنال، یافته، ابزار، اقدام |

| `SeverityBar` | `severity`, `category` | فهرست سیگنال‌ها |

## تبدیل شناسه‌های داخل متن به chip

`reasoning_fa` و `rationale_fa` شناسه‌ها را داخل متن دارند:

```js
const EV = /\[?(EV-[A-Za-z0-9_-]+)\]?/g;

function renderWithEvidence(text) {
  return text.split(EV).map((part, i) =>
    i % 2 === 1 ? <EvidenceChip key={i} id={part} /> : part
  );
}
```

## کش سمت کلاینت

| داده | کلید | باطل می‌شود وقتی |
|---|---|---|
| `/agents`, `/tools` | ثابت | هرگز — یک بار در بوت |
| `/summary`, `/customers` | `as_of` | تغییر `as_of` |
| `/customers/:id` | `as_of` + `id` | تغییر `as_of` |
| `/evidence/:id/rows` | `as_of` + `id` | تغییر `as_of` |
| `/actions` | `as_of` + `limit` | تغییر `as_of` یا **هر `POST /feedback`** |
| meeting | `as_of` + `id` + `agents` | تغییر `as_of` |

## حالت‌های خالی

سرور تقریباً هرگز آرایهٔ خالی بی‌توضیح برنمی‌گرداند. هرجا `empty_reason_fa` یا `reason_fa` هست همان را نشان دهید، نه متن عمومی خودتان.

| حالت | به‌جای «داده‌ای نیست» |
|---|---|
| ابزار چیزی برنگرداند | `result.empty_reason_fa` |
| تحلیل‌گر بیدار نشد | `skipped[].reason_fa` |
| حلقهٔ باز نیست | «موردی باز نیست» با ظاهر مثبت، نه خالی |
| مشتری سیگنال ندارد | «هیچ آشکارسازی روی این مشتری فعال نشده است» |

# هفت چیزی که نباید بکنید

1. **عددی از `payload` را داخل جملهٔ خودتان ننویسید.** کل ارزش محصول این است که هر عدد یک شاهد پشتش دارد؛ جملهٔ ساختهٔ فرانت این زنجیره را می‌شکند.
2. **شناسهٔ شاهد را بدون قابلیت کلیک نشان ندهید.** شناسه‌ای که باز نمی‌شود یک باگ است.
3. **مسیرهای پولی را با `useEffect` بی‌شرط صدا نزنید.** refresh مرورگر نباید هزینه بسازد.
4. **تحلیل‌گرهای بیدارنشده را حذف نکنید.** «چرا این را نگاه نکردی» همان‌قدر مهم است که «چه دیدی».
5. **قیدها را در هر کارت تکرار نکنید.** بک‌اند عمداً از تحلیل‌گرها خواسته تکرارشان نکنند؛ یک بار بالای دستور جلسه کافی است.
6. **ستون‌های `/evidence/:id/rows` را hardcode نکنید.** بسته به شیت فرق می‌کنند.
7. **`source: "rules"` را پنهان نکنید.** یعنی مدل در دسترس نبوده و متن قالبی است — کاربر باید بداند.
